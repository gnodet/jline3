# PR Review Loop

Automated loop that discovers, triages, and reviews open PRs on JLine3.
Uses sub-agents for parallel review and verification, and the oss-helper
`review-pr.md` guideline for the actual review logic.

## Architecture

```
Main loop (orchestrator)
  +-- Step 1-4: Triage (inline -- fast, low cost)
  |
  +-- Step 5: Review (sub-agents, parallel)
  |     +-- Reviewer agent PR #1234
  |     +-- Reviewer agent PR #5678
  |     +-- Reviewer agent PR #9012
  |
  +-- Step 6: Verify (sub-agents, one per review)
  |     +-- Verifier agent PR #1234  <- checks reviewer's findings
  |     +-- Verifier agent PR #5678
  |     +-- Verifier agent PR #9012
  |
  +-- Step 7-8: Post & update state (inline)
```

- **Reviewer agents** do the deep review work (read diff, git history, project rules).
  Each runs in parallel to avoid serializing expensive diff analysis.
- **Verifier agents** independently check each reviewer's findings for false positives
  before anything is posted to GitHub. This is the maker/checker split.
- **No worktrees needed** -- reviews are read-only (diffs come from `gh pr diff`).
  Worktrees would only be needed if the loop evolved to propose code fixes.

## Execution Steps

### 1. Read Current State

Read `STATE.md` from the repository root. Parse:

- The list of already-reviewed PRs (by number) and their review dates
- The list of skipped PRs (by number) and their skip reasons
- The timestamp of the last run

### 2. Fetch Open PRs

List all open, non-draft PRs:

```bash
gh pr list --repo jline/jline3 \
  --search "is:pr is:open -is:draft" \
  --limit 30 \
  --json number,title,author,createdAt,updatedAt,labels,reviewDecision,additions,deletions,changedFiles
```

### 3. Filter PRs

Remove from the list:

- PRs already in the "Reviewed PRs" table in STATE.md **unless** their `updatedAt`
  is newer than the recorded review date (re-review needed)
- PRs in the "Skipped PRs" table -- **but NOT if their `reviewDecision` is
  `CHANGES_REQUESTED` and they have been updated since the skip was recorded**.
  PRs where we (or any AI reviewer) previously requested changes must be
  re-reviewed once the author pushes updates. When a previously-skipped
  CHANGES_REQUESTED PR has a newer `updatedAt` than its skip date, remove it
  from the Skipped table and include it in the review candidates.
- PRs authored by bots: `dependabot`, `renovate`, `github-actions`
- PRs with label `dependencies` (dependency bumps -- skip unless they touch code)
- PRs that already have an oss-helper review. To detect this, check if any existing
  review comment on the PR contains the oss-helper attribution string
  `"This review was generated by an AI agent"`. Use:
  ```bash
  gh api repos/jline/jline3/pulls/<NUMBER>/reviews --jq '.[].body' | grep -q "This review was generated by an AI agent"
  ```
  If the grep matches, the PR has already been reviewed by oss-helper -- skip it
  **unless** the PR has been updated since that review (compare `updatedAt` with the
  review's `submitted_at`):
  ```bash
  gh api repos/jline/jline3/pulls/<NUMBER>/reviews \
    --jq '[.[] | select(.body | test("This review was generated by an AI agent"))] | max_by(.submitted_at) | .submitted_at'
  ```
  If the PR's `updatedAt` is newer than the last AI review's `submitted_at`, keep it
  for re-review. Otherwise, skip it.

### 4. Triage and Prioritize

Sort remaining PRs by priority:

1. **High priority** -- PRs with `reviewDecision` = `REVIEW_REQUIRED` and no reviewer
   activity, or PRs older than 7 days without review
2. **Medium priority** -- PRs with recent updates
3. **Low priority** -- PRs that already have reviews from others

Log a summary:

```
## PR Triage Summary (<date>)

Found <N> open PRs, <M> need review.

### High Priority
- #XXXX: <title> by <author> -- <reason>

### Medium Priority
- #XXXX: <title> by <author>

### Low Priority
- #XXXX: <title> by <author>
```

Select the top 3 PRs by priority for review.

### 5. Review PRs (Parallel Sub-agents)

For each selected PR, spawn a **reviewer sub-agent** using the Agent tool
with `model: "opus"` and thinking at max effort.
Launch all reviewer agents in a single message so they run concurrently.

Each reviewer agent prompt must include:

```
You are reviewing PR #<NUMBER> on jline/jline3.

IMPORTANT: Before doing anything else, read and follow the oss-helper review-pr
guideline. This is the canonical review process for this project:

1. Read the oss-helper skill and review guideline:
   - Read .claude/skills/oss-helper/SKILL.md (initialization steps)
   - Read .claude/skills/oss-helper/review-pr.md (the review process)

2. Run the oss-helper initialization:
   - Detect project from git remote
   - Load project rules from .oss-ai-helper-rules/
     (project-info.md, project-standards.md, project-guidelines.md)

3. Follow review-pr.md steps 1-6 exactly:
   - Parse the PR number
   - Fetch PR metadata and diff via gh
   - Investigate git history of modified files (git log, git blame)
   - Review against the loaded project rules
   - Evaluate for issues (missing tests, regressions, convention violations, etc.)

4. Return your findings as structured output (do NOT follow review-pr.md steps 7-8
   about posting to GitHub -- the main loop handles that):

   VERDICT: <APPROVE|COMMENT|REQUEST_CHANGES>

   SUMMARY: <1-2 sentence overall assessment>

   FINDINGS:
   - [SEVERITY: high|medium|low] [FILE: path/to/file] [LINE: N] <description>
   - ...

   SUGGESTION_BLOCKS:
   - [FILE: path/to/file] [START_LINE: N] [END_LINE: M]
     ```suggestion
     <corrected code>
     ```

   GENERAL_COMMENTS:
   - <comment not tied to a specific line>

Return ONLY the structured output above -- no preamble, no markdown headers.
```

### 6. Verify Findings (Parallel Sub-agents)

After all reviewer agents complete, spawn a **verifier sub-agent** (with `model: "opus"`
and thinking at max effort) for each review that returned
findings (verdict != APPROVE).
Launch all verifiers in parallel.

Each verifier agent prompt must include:

```
You are a verification agent. A reviewer found the following issues in PR #<NUMBER>
on jline/jline3. Your job is to independently check each finding and determine
whether it is a TRUE issue or a FALSE POSITIVE.

Be skeptical. Default to marking findings as false positives unless you can
independently confirm the issue by reading the diff and git history yourself.

PR DIFF (fetch fresh):
  gh pr diff <NUMBER> --repo jline/jline3

REVIEWER'S FINDINGS:
<paste the reviewer's structured output here>

For EACH finding, independently verify:
1. Does the file and line reference exist in the diff?
2. Is the finding actually a problem, or is it correct code?
3. Does git history show this was intentional? (git log, git blame)
4. Does it actually violate the cited rule?

Return your verification as:

VERIFIED_FINDINGS:
- [FINDING: <original finding summary>] [VERDICT: confirmed|false_positive] [REASON: <why>]
- ...

FINAL_VERDICT: <APPROVE|COMMENT|REQUEST_CHANGES>
FINAL_SUMMARY: <updated summary after removing false positives>

Return ONLY the structured output above.
```

### 7. Post Reviews to GitHub

For each PR where the verifier confirmed at least one finding, post the review
to GitHub. Only include **verified findings** (not false positives).

Build the review using the GitHub API:

```bash
gh api repos/jline/jline3/pulls/<NUMBER>/reviews --input - <<'EOF'
{
  "event": "<COMMENT|REQUEST_CHANGES|APPROVE>",
  "body": "<FINAL_SUMMARY>\n\n_This review was generated by an AI agent and may contain inaccuracies. Please verify all suggestions before applying._\n\n_Claude Code on behalf of Guillaume Nodet_",
  "comments": [
    {
      "path": "<file>",
      "line": <line>,
      "side": "RIGHT",
      "body": "<finding description or suggestion block>"
    }
  ]
}
EOF
```

For PRs where all findings were marked as false positives by the verifier,
do NOT post a review. Log this:

```
PR #XXXX: All <N> findings were false positives. No review posted.
```

For PRs where the reviewer returned APPROVE (no findings), always post
an approving review to GitHub regardless of diff size.

### 8. Update State

After all reviews are posted (or skipped):

1. Update the "Last Run" section in STATE.md:
   - Current timestamp
   - Number of PRs checked
   - Number of reviews posted

2. Add reviewed PRs to the "Reviewed PRs" table with date and verdict

3. Add skipped PRs (bot, etc.) to the "Skipped PRs" table.
   **Never permanently skip a PR whose `reviewDecision` is `CHANGES_REQUESTED`.**
   Those PRs should remain trackable via the AI-review-detection filter so they
   are automatically re-reviewed when the author pushes updates. Only add PRs to
   the Skipped table for permanent reasons: bot authorship, `DO NOT MERGE` title,
   or `dependencies` label. **Do NOT skip PRs for being too large** -- review
   all PRs regardless of diff size. PRs with prior AI reviews (whether APPROVE
   or CHANGES_REQUESTED) that have not been updated since the last review are
   simply filtered out by the AI-review-detection logic in Step 3 and do NOT
   need a Skipped table entry.

4. Clear the "Review Queue" and repopulate with remaining unreviewed PRs

### 9. Push State to Fork

After updating STATE.md and loop-run-log.md, commit and push the updated state
files to the `pr-review-loop-state` branch on the `gnodet` remote so that state
is persisted in GitHub across sessions.

```bash
git checkout pr-review-loop-state
git add STATE.md loop-run-log.md loop-budget.md loop-constraints.md loop-ledger.json
git commit -m "Update review loop state after run $(date -u +%Y-%m-%dT%H:%M:%SZ)"
git push gnodet pr-review-loop-state
git checkout master
```

If the branch or remote doesn't exist yet, skip this step and log a warning.
Never force-push. If the push fails (e.g. diverged history), log the error
and continue -- state is still saved locally.

### 10. Summary

Output a brief summary:

```
## Loop Complete

- Reviewed: <N> PRs (<M> reviews posted, <K> suppressed by verifier)
- Skipped: <P> PRs
- False positive rate: <X>% (<F> findings rejected by verifier out of <T> total)
- Remaining in queue: <R> PRs
- Next high-priority: #XXXX (<title>)
```

## Constraints

You MUST:
- Read STATE.md before fetching PRs to avoid re-reviewing
- Spawn reviewer agents in parallel (all in one message)
- Spawn verifier agents in parallel (all in one message) after reviewers complete
- Only post verified findings -- never post unverified reviewer output directly
- Post reviews with the AI-generated disclaimer
- Update STATE.md after every run
- Respect the 3-PR-per-iteration limit
- Include `_Claude Code on behalf of Guillaume Nodet_` in all review comments

You MUST NOT:
- Merge, close, or label any PR
- Review draft PRs
- Post a review without running the verifier first
- Post reviews where all findings were false positives
- Skip the git history investigation step in reviewer agents
- Review more than 3 PRs in a single loop iteration
